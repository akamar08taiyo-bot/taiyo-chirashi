# Claude Code 引き継ぎ用・確定仕様 完全版

> **この文書を本アプリの要件の最上位ソース（Source of Truth）として扱うこと。**
> 新しい要件ヒアリングを最初からやり直さない。重大な矛盾・外部サービス認証情報・会社として判断が必要な事項だけ確認し、それ以外はこの仕様に従って自動的に実装・デバッグを進める。

## 0. 引き継ぎ時の絶対ルール

- 最初にリポジトリ／ZIPを展開し、**文章ではなく実コードを確認**する。
- `approved-concept.png` と現行STEP3系UIを承認済みデザインとして扱い、ブラウン・ベージュ基調と3カラム編集UIを勝手に全面変更しない。
- デモ画面で終わらせず、可能な限り社内運用レベルまで実装する。
- モックで動いたことを「本番完成」と表現しない。Supabase / OpenAI等のライブ接続未確認は明示する。
- 秘密情報をソースへ直書きしない。
- 実装後は型チェック、ビルド、単体テスト、統合テスト、ブラウザE2E、PC／スマホ、A4出力、権限、オフライン、競合、エラー表示を実際に確認する。
- 発見した修正可能な不具合はその場で直し、再テストする。

## 1. アプリの目的

太陽シルバーサービス社内で、Word・PowerPoint・Canva等を細かく操作せず、写真と文章を入れるだけで以下を5〜10分程度で作成できるWebアプリを作る。

1. 福祉用具レンタルのチラシ
2. 福祉用具・住宅改修等の事例集
3. 施設・病院等へ販売する消耗品の商品チラシ

PCを主要編集端末とし、スマートフォンではログイン、過去作品確認、写真アップロード等を行えるようにする。A4の細かな編集はPC中心でよい。

## 2. UXの最優先原則

- 初めて触る社員でも迷いにくい。
- 中央のA4完成プレビューを編集画面の主役にする。
- 自由配置型Canvaのようにレイアウトを壊せる設計ではなく、**テンプレート方式**を基本とする。
- 最初から大量の設定を見せない。新規作成は原則3STEP。
- 入力は即時プレビュー反映。保存ボタンを押すまで画面が変わらない設計は禁止。
- 技術用語を一般社員向けエラーへ出さない。次に何をすべきか日本語で示す。
- 長文や画像比率の違いでもA4が崩れにくい。

## 3. 作成モード（最上位切替）

編集対象には `mode` を持たせ、最低限以下の3種類を切り替えられること。

| mode | 画面表示名 | 主用途 | 単位数 | 1〜3割負担 | 消耗品価格 |
|---|---|---|---|---|---|
| `rental` | レンタル | 福祉用具レンタルチラシ | 対応 | 対応 | 不要 |
| `cases` | 事例集 | 福祉用具・住宅改修等の事例集 | 対応可 | 対応可 | 不要 |
| `consumables` | 消耗品 | 施設・病院向け消耗品チラシ | **非表示** | **非表示** | 対応 |

- 編集中にモード切替ができる。入力済みデータを勝手に削除しない。
- 保存データにもmodeを保持し、複製・テンプレート・再読み込み後も同じモードで復元する。
- 旧データにmodeが無い場合、安全な推定／デフォルトで互換復元する。
- 消耗品モードでは福祉用具専用の「単位数」「1割・2割・3割負担」をUI・A4・PDF・PNG/JPEG・印刷から出さない。

## 4. 新規作成フロー

原則3STEPにする。

### STEP1：何を作るか
- レンタル
- 事例集
- 消耗品
- A4縦／横も分かりやすい位置で指定可能にする。

### STEP2：写真／商品数
- 1 / 2 / 3 / 4 / 6 / 9
- 消耗品では「写真枚数」ではなく「商品数」と表現する。
- 9は基本3列×3段。

### STEP3：テンプレート
- 選んだモードに合うテンプレートを優先表示。
- 「白紙から作成」も必ず用意。
- テンプレートから作成後も全項目を通常編集できる。

## 8. 写真

- ファイル選択とドラッグ＆ドロップ両方。
- 9枚まとめてドロップしたら枠1〜9へ順番に配置。
- 写真カード同士をドラッグで並べ替え。
- 写真ごとに拡大、縮小、上下左右位置、トリミング相当、回転、差し替え、削除。
- UIは画像編集ソフト化せず、簡単さ優先。

### 縦長・横長写真
- どちらにも対応。
- 写真ごとに `contain` 相当の「写真全体を表示」と `cover` 相当の「枠いっぱいに表示」を切替。
- 新規写真は全体が確認しやすい安全な表示を初期値とする。
- その後、拡大・位置調整で仕上げられる。

### 将来拡張
- 写真上へ文字、矢印、丸囲み等を置ける構造を想定。ただし主要機能より優先しない。

## 9. レンタル／事例集モードの商品・料金項目

各写真／項目に最低限以下を保存。
- 番号
- タイトル
- 説明文
- 商品名
- 品番
- 単位数
- 月額または料金基準

空欄項目があってもA4レイアウトを壊さない。

### 単位数
- チラシ全体で表示ON/OFF。
- 例：`300 単位／月`。

### 利用者負担
- 1割、2割、3割を個別ON/OFF。複数同時表示可。
- 基準金額から自動計算。
- 例：3,000円 → 300円 / 600円 / 900円。
- 端数処理ロジックは1箇所へ集約し、将来ルール変更可能にする。

## 11. 長い商品名の表示品質

特に消耗品の商品名は、単純なブラウザ自動折り返しで不自然な位置に改行しない。

優先順：
1. まず1行で収まるか判定。
2. 少し長い場合はフォントサイズを段階的に縮小。
3. それでも長い場合は最大2行を基本とし、意味の切れ目に寄せて改行。
4. ユーザーが手動改行した場合はその位置を最優先。
5. 括弧 `（...）` の途中、型番・容量の途中などを極力分断しない。
6. `・ / ／ - ：` や空白、規格・容量の前など自然な境界を候補にする。
7. 区切り記号自体は商品名の一部なので勝手に削除しない。
8. それでも収まらない場合は出力前チェックで「商品03の商品名が長すぎます」等、具体的な修正箇所を示す。

## 12. 文言サンプル

- 多数の文言サンプルを用意し、選ぶだけで入力できる。
- 選択後に自由編集可能。
- サンプルにない文章は完全手入力可能。
- 現行実装は合計226件、そのうち消耗品43件。今後増やしてよい。
- 対象：文書タイトル、サブタイトル、各写真／商品タイトル、説明、フッター見出し、フッター補足。
- 消耗品モードでは福祉用具向け文章を大量に混ぜず、消耗品／共通候補を中心に表示。

## 13. デザイン

- 自由度を上げすぎない。
- スタイル例：標準、シンプル、やわらかい、商品紹介。
- メインカラー：ブラウン、ブルー、グリーン、オレンジ、その他。
- メインカラーを変えると見出し、枠線、番号、フッター等がまとめて変わる。
- 社員がCSSや余白を個別調整するUIは作らない。
- 既存の落ち着いた福祉系ブラウン／ベージュデザインを基本正解とする。

## 14. 文章はみ出し・自動調整

- タイトル・説明が一定範囲なら自動フォント調整。
- それでも収まらない場合は出力前にエラー／警告。
- 例：「写真03の説明文が長すぎます」「商品03の商品名が長すぎます」。
- DOM上の縦・横overflowも検出対象にする。

## 15. AI文章補助

初期版最低2機能：
1. 「AIで文章を整える」：既存文章を自然で分かりやすい事例集／チラシ向け文章に整える。
2. 「メモから説明文を作る」：短い事実メモから説明文候補を作る。

### AIの絶対制約
- 入力されていない事実を勝手に追加しない。
- 病名、身体状況、障害、利用者属性、商品名、メーカー、品番、設置状況を推測しない。
- 消耗品ではさらに規格、容量、入数、価格も推測しない。
- AI結果を本文へ自動上書きしない。
- 「AIからの提案」として表示し「この文章を使う」「やり直す」で採用をユーザーに委ねる。
- OpenAI APIキーをブラウザへ露出させない。Supabase Edge Function等のサーバー側から呼ぶ。

## 17. 自動保存・オフライン

- 操作停止後約1〜2秒でデバウンス自動保存。
- 1文字ごとにサーバー通信しない。
- 状態表示：「保存中…」→「✓ 保存しました」。
- サーバーだけに依存せずIndexedDB等へローカル下書き。
- オフライン文言例：「現在オフラインです。変更内容はこのPCに保存しています。通信が戻り次第、自動保存します。」
- 復旧時に未保存変更を自動同期。
- ブラウザを誤って閉じても可能な範囲で直前状態を復元。
- 共用PCで別社員の下書きが混ざらないよう、ローカル下書きをユーザー単位で分離。

## 18. 編集競合

- 完全リアルタイム共同編集は不要。
- version + updated_at等で楽観的ロック。
- 別社員が先に更新済みなら無条件上書き禁止。
- 「この事例集は別のユーザーによって更新されています」等の一般向け表示。
- 選択肢：最新状態を確認／自分の内容を複製して残す。

## 19. 複製・テンプレート

### 複製
- 既存作品を複製し、写真・文章等だけ変更して新規作品化。
- モード、レイアウト、全編集状態を引き継ぐ。

### テンプレート
- 個人／営業所／全社の共有範囲。
- 例：屋内手すり9枚、屋外手すり9枚、自費ベッド4枚、住宅改修2枚、消耗品6商品など。
- モードをテンプレートへ保存。

## 20. 写真ライブラリ

- 大きく「商品写真」「事例写真」。
- 商品写真：手すり、ベッド、歩行器、スロープ、消耗品等のカテゴリー。
- 事例写真：「自分だけ」「営業所」「会社共有」。
- 検索対応。将来：カテゴリー、メーカー、商品名等で絞り込み。
- スマホ高解像度画像は元画像と編集用軽量画像を分離。
- 編集画面では軽量版、高品質出力では元画像を優先。

### セキュリティ
- Storageは原則非公開。
- 事例写真を無条件公開URLにしない。
- 権限のある社員へ署名付きURL等で提供。
- 署名付きURLそのものを永続DBへ保存せず、mediaId等の恒久参照を保存。
- 非公開写真を共有作品へ貼った場合、写真ライブラリ自体を公開せず、作品閲覧権限がある社員が作品内だけで画像を取得できる構造。

## 21. 認証・権限

ログインは社員ID＋パスワード。ユーザーにメールアドレスを入力させない。

Supabase Auth利用時、内部的メールが必要なら社員IDから内部認証IDへ変換し、画面へ見せない。パスワード平文保存は禁止。

### ロール
1. 一般社員
2. 営業所管理者
3. 全社管理者

### 一般社員
- 作成・編集・保存・複製
- PDF/PNG/JPEG/印刷
- 写真アップロード／ライブラリ
- AI文章補助

### 営業所管理者
- 一般社員機能 + 自営業所の社員管理、営業所情報、営業所テンプレート等。

### 全社管理者
- 全営業所、全社員、会社情報、全社テンプレート、全社写真ライブラリ等。

### 退職者
- レコード削除ではなく `is_active=false` を基本。
- 過去作品は残す。

## 22. 作品共有範囲・RLS

各作品：
- 自分だけ (`private`)
- 同じ営業所 (`office`)
- 会社全体 (`company`)

画面で隠すだけは禁止。PostgreSQL Row Level Security等でサーバー側制御。

必須アクセス例：
- 他社員のprivate作品を一般社員が取得不可。
- 他営業所のoffice作品を取得不可。
- company作品は同一会社内で取得可。
- 全社管理者でも他社員のprivate作品は通常閲覧対象にしない。
- 権限のないIDをRESTへ直接指定しても本文を返さない。

共同編集は完全リアルタイムではないが、閲覧権限のある共有作品を複数社員が編集し得るためversion競合検知を必須とする。共有範囲・営業所・作品担当等の管理系メタデータ変更はUIだけでなくサーバー側でも所有者／管理者権限を守る。

## 23. 削除

- 即完全削除しない。
- 削除 → ゴミ箱 → 一定期間（現行30日）→ 完全削除。
- 権限があれば復元可能。

## 26. ユーザー向けエラー

技術用語・HTTP内部文言をそのまま出さない。
